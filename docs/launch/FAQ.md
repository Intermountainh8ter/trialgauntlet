# FAQ: the hard questions

Honest answers. Every number is either from the committed baseline result files (regenerated by
`scripts/regenerate_results.sh`) or from the committed Qwen3 result files (`results/qwen3-*-n4.json`), and matches the
README tables, which are generated from those files. Real-model results exist now, but they are narrow: read the
limits below before quoting any of them.

## Has this been run on a real model?

Yes, in one narrow way. Qwen3 4B, 8B and 14B as Q8_0 GGUFs under llama.cpp (HIP) on one AMD gfx906 machine,
temperature 0.7, top-p 0.8, top-k 20, all 138 tasks across `fleet`, `ledger` and `config`, n=4 trials per task, k=2
(552 trials per arm). Stock and ablated pairs at 8B and 14B and a 4B stock row share one Qwen3 chat template file; a
second 4B stock row uses the model's own embedded template. The tables are in the README. Runs against the
built-in mock server are still labelled `MOCK` and say nothing about any model. The injection and fault suites have
not been run on any model.

## What did the real-model runs show?

Three things, each with a caveat.

1. **pass^2 is below pass@1 in every cell that passes anything.** 8B stock on `fleet`: pass@1 55.3%, pass^2 40.1%;
   on `ledger` 42.9% and 29.0%. The 14B gaps are smaller (1.8 to 4.6 points); the 8B gaps are 5.7 to 15.2 points.
2. **Stock versus ablated differs on some environments, not others.** 8B: `fleet` 55.3% vs 54.3% and `ledger`
   42.9% vs 42.9% pass@1 are indistinguishable; `config` is 15.3% vs 5.7% pass@1 and 8.0% vs 0.0% pass^2. 14B:
   outcome-only success is about the same in both arms, but pass@1 is lower for ablated on `ledger` (37.5% vs 19.6%)
   and `config` (22.7% vs 13.6%) and the same on `fleet` (46.6%). Policy violations per trial over the whole
   benchmark: 8B 0.09 vs 0.21, 14B 0.40 vs 0.60.
3. **The 4B stock row is a format artefact.** 0.0% on every metric: under the shared chat template the model's tool
   calls came out as plain text and were not parsed (13 tool calls executed in total across 552 trials). The row is
   kept as run. Under its own embedded template the same model produced parsed tool calls: pass@1 of 28.8% on `fleet`,
   3.6% on `ledger`, 1.1% on `config`, but 373 of 552 trials still ended in `no_action`, so it is a weak result with
   a residual format component, not a clean capability number.

## What do the real-model runs not show?

That any of this holds beyond these conditions. The environments are small and synthetic, the users are keyword
rules, and the graders and the oracle were written by the same person. It is one machine, one run configuration and
one model family. n=4 trials per task is small and cell-level differences are noisy: the 95% intervals overlap in
every stock-vs-ablated pair, including the largest ones (8B `config`, 14B `ledger`). Read them as leads for a larger
run, not as established effects. The exact 8B and 14B checkpoints are not recorded in the repository (only the
served aliases and sampling settings), and raw trajectories are not committed.

## What do "stock" and "ablated" mean?

"Stock" is the unmodified Qwen3 release; "ablated" is an abliterated variant of the same size (weights edited to
remove refusal behaviour), served the same way. Each pair is a comparison of two specific checkpoints, not of
abliteration in general.

## Do the results rank the model sizes?

No. 14B stock is higher than 8B stock on `config` (22.7% vs 15.3% pass@1) and lower on `fleet` (46.6% vs 55.3%) and
`ledger` (37.5% vs 42.9%). About 30% of 8B trials ended in `no_action` (167 of 552 stock, 171 ablated) and none of the
14B trials did, so the two sizes are not compared on equal behaviour. A trial with no actions cannot violate a policy,
which may deflate the 8B violation counts.

## Did you have to correct anything?

Yes, once. An earlier version of the README gave an "overall" policy-violation rate for the 8B pair that was really
the `config` environment's share of trials with a violation. The README now carries a dated correction note and the
trial-weighted per-trial figures (8B 0.09 vs 0.21, 14B 0.40 vs 0.60). No pass metric changed.

## Why another agent benchmark?

It is not meant as a general benchmark; tau-bench, ReliabilityBench, Agent Reliability Lab and others exist and are
broader. This repository is a narrow, tiny, deterministic, dependency-free harness built around two checks that are easy
to skip: pass^k next to pass@k, and a degenerate-success audit of every environment.

## What is pass^k and why not just average more runs?

pass^k is the probability that all k independent trials of a task succeed. Averaging more runs gives a better estimate of
pass@1, which still hides whether the successes are spread evenly or concentrated. Example (n=8, c=6, k=4): pass@1 is 75%
but pass^4 is about 21%. Derivation and the unbiased estimator `C(c,k)/C(n,k)`: `docs/METHODOLOGY.md`.

## What is the degenerate-success audit, and what did it find?

Every environment ships no-op, random-tool and always-refuse baselines plus a scripted oracle and a greedy-unsafe agent.
`trialgauntlet audit` flags an environment if a trivial baseline passes more than a threshold (default 5%), if the oracle
is below 100%, or if the shortcut agent passes. On the three built-in environments the trivial baselines passed 0.7% or
less (random-tool on `fleet`: 3 of 416 trials). No environment needed to be changed after the first audit run, because
the design rules were chosen up front. That is not proof that no cheap strategy exists: see
`docs/THREATS_TO_VALIDITY.md`. The audit covers the scripted baselines; it was not rerun on the Qwen3 arms.

## Does it reproduce the "do-nothing agent scores well on tau-bench" finding?

No, and it does not claim to. A 2025 paper on agentic benchmark rigor reported that a do-nothing agent scored well on parts
of tau-bench; we cite that from memory of the abstract and have not re-run tau-bench. What the repository shows is the
mechanism on its own tasks: against a deliberately naive grader (`<env>+naive`) a do-nothing agent passes 30.8%, 35.7% and
36.4% of tasks, against the real graders 0%.

## Why no LLM user simulator or LLM judge?

A stochastic user makes "the agent was inconsistent" and "the simulator was inconsistent" indistinguishable, which defeats a
reliability measurement. Scripted users and code graders mean any difference between two trials of the same task comes from
the agent or the model server. The price is realism: scripted users are keyword rules.

## Is the grading fair?

It encodes the author's reading of the written policies in each environment, including judgement calls (windows, thresholds,
capacity floors). The scripted oracle proves each task is solvable under that reading; it does not prove the reading is the
only sensible one, and the oracle and the graders share an author. There has been no human validation of the graders.

## Do the injection results say anything about a model?

No. The suite is demonstrated with scripted agents only (a gullible one that obeys text in tool results, and the oracle that
does not); the Qwen3 runs used the plain environments, without the injection or fault wrappers. The injected text is three
fixed templates, not adaptive attacks, and attack success must be read together with exposure (an agent that never reads a
poisoned tool has 0% for free).

## Will it work with my local server?

Run `trialgauntlet doctor --base-url http://127.0.0.1:8080/v1` first. It checks reachability and whether the server returns
structured tool calls. For llama.cpp that means `llama-server --jinja`, and the chat template matters: the 4B result above
is an example of what a template mismatch looks like. The committed Qwen3 runs used llama.cpp on Linux.
The Windows commands in the README were not executed on Windows, and the README's example command targets Qwen3-Coder, which
was not run.

## Does temperature matter?

Yes. At temperature 0 all trials of a task are identical and pass^k equals pass@1; the harness cannot show inconsistency that
sampling does not produce. The Qwen3 runs used temperature 0.7, top-p 0.8 and top-k 20. Use the sampling settings your model
recommends and report them with the result.
